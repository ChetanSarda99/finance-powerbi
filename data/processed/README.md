# Processed star schema - finance-powerbi

Generated by [`../process.py`](../process.py) from the two raw City of Vancouver
capital CSVs in [`../raw/`](../raw/). These are the load-ready tables for the
Power BI model in [`../../docs/model-diagram.md`](../../docs/model-diagram.md) and
the DAX measures in [`../../docs/measures.md`](../../docs/measures.md).

Regenerate with:

```
cd ~/Projects/Self/career-ops/notion/projects/finance-powerbi
python3 data/process.py
```

Everything is real public data under the Open Government Licence - Vancouver. No
synthetic rows. No network access at process time (reads the local raw CSVs).

Last generated: 2026-06-01.

## Why the shape is "long" not "wide"

The raw CSVs are WIDE: each project is one row with many money columns (one per
year / scenario / funding split). DAX time-intelligence and the IBCS variance
grammar need a LONG (tidy) fact: one row per (project x scenario x period) with
a single `amount` column the measures `SUM`. `process.py` unpivots the wide
columns into that long fact and builds conformed dimensions around it.

## Fact schema (`fact_capital_finance.csv`)

| Column | Type | Meaning |
|---|---|---|
| `project_program_name` | text | the specific capital project / program (degenerate dimension) |
| `account_key` | int FK -> `dim_account.account_key` | which raw budget line the amount came from |
| `period_key` | int FK -> `dim_period.period_key` | the fiscal year |
| `costcenter_key` | int FK -> `dim_costcenter.costcenter_key` | the 3-level service-category leaf |
| `business_unit_key` | int FK -> `dim_business_unit.business_unit_key` | top-level program |
| `scenario` | text FK -> `dim_scenario.scenario_code` | one of PY / AC / PL / FC |
| `amount` | number | the dollar value (the measure target) |

`Total Amount = SUM ( fact_capital_finance[amount] )` is the foundation measure;
everything else filters this by `scenario` and `period`.

Zero / blank cells are dropped (mirrors the M-script `NonZero` filter), so the
fact only carries rows with real dollars.

## Dimension schemas

`dim_account.csv` -- `account_key`, `account_code`, `account_label`,
`account_default_scenario`, `source_file`.

`dim_period.csv` -- `period_key`, `year`, `label` ("FY2026"). Year-grain only
(no full Date table); the DAX measures (see measures.md performance notes) shift
years explicitly rather than via `SAMEPERIODLASTYEAR`.

`dim_costcenter.csv` -- `costcenter_key`, `service_category_1`,
`service_category_2`, `service_category_3`, `business_unit_key`. This is the
drill hierarchy: program (_1) -> sub-program (_2) -> area (_3).

`dim_business_unit.csv` -- `business_unit_key`, `business_unit_name`. The
service_category_1 rollup; this is the RLS boundary in the model diagram.

`dim_scenario.csv` -- `scenario_code`, `scenario_label`, `fill_style`. The IBCS
fill grammar: AC=solid_black, PL=outlined, FC=hatched, PY=solid_grey.

## Raw-column -> IBCS-scenario mapping decisions (the honest part)

The IBCS set is PY (Prior Year), AC (Actual), PL (Plan / Budget), FC (Forecast).
Vancouver capital data is approved-budget data, not a transaction ledger, so
"Actual" is mapped as a realized-spend proxy: an approved budget for a year that
has already elapsed (today is 2026). Every decision below is deliberate; columns
that do not cleanly match one scenario are NOT loaded (see "Not loaded").

From `vancouver-2023-2026-capital-plan.csv`:

| Raw column | Scenario | Period | Rationale |
|---|---|---|---|
| `2023_2026_capital_plan_city_led_allocations_2023_approved_budget` | AC | 2023 | approved budget for a year that has elapsed -> realized-spend proxy (Actual) |
| `..._2024_approved_budget` | AC | 2024 | same, elapsed year |
| `..._2025_approved_budget` | AC | 2025 | same, elapsed year |
| `2023_2026_capital_plan_city_led_allocations_2026_budget` | PL | 2026 | current active year approved budget, not yet spent -> Plan |
| `multi_year_capital_project_budgets_previously_approved` | PY | 2022 | budgets approved in PRIOR plan windows (a cumulative prior bucket) -> Prior Year, anchored to the pre-window year 2022 |

From `vancouver-2026-capital-project-budget.csv`:

| Raw column | Scenario | Period | Rationale |
|---|---|---|---|
| `annual_capital_expenditure_2026_capital_expenditure_budget` | PL | 2026 | 2026 approved annual expenditure budget -> Plan |
| `annual_capital_expenditure_2027_forecast` | FC | 2027 | column is literally labelled "forecast" -> Forecast |
| `annual_capital_expenditure_2028_forecast` | FC | 2028 | same |
| `annual_capital_expenditure_2029_forecast` | FC | 2029 | same |
| `annual_capital_expenditure_2030_forecast` | FC | 2030 | same |

### Honesty notes / caveats

- "Actual" here is an approved-budget-for-an-elapsed-year proxy, NOT an audited
  expenditure ledger. Vancouver does not publish a per-project actual-spend
  column in these datasets. This is the same assumption the existing M-script
  (`docs/power-query-m.md`) and DAX measures already make. It is documented so a
  reviewer is never misled into thinking AC is cash-settled spend.
- 2026 appears as PL from BOTH files (the capital-plan 2026 budget line and the
  capital-project-budget 2026 expenditure budget). They are different source
  measures (distinguished by `account_key`), so they are intentionally NOT
  merged; treat them as two PL line types and slice by account if you want one.
- PY is anchored to fiscal year 2022 because the "previously approved" column is
  a cumulative prior-window total with no single year. 2022 is the year-before
  the 2023-2026 plan window, so it reads cleanly as "before this plan".

### Columns deliberately NOT loaded

These are alternative cuts of the SAME dollars; loading them as fact rows would
double-count against the per-year scenario buckets:

- Plan rollup totals: `2023_2026_original_capital_plan`,
  `changes_to_2023_2026_capital_plan_*`, `2023_2026_revised_capital_plan`,
  `revised_..._funding_development_contributions_*`, `revised_..._funding_city_led`,
  `remainder_of_2023_2026_capital_plan`.
- Forecast/availability snapshots:
  `spending_forecast_of_total_open_project_budgets_till_year_end_2025`,
  `available_project_budget_in_2026`.
- Funding-source splits in the project-budget file:
  `2026_new_multi_year_capital_project_budgets_requests*` (pay-as-you-go,
  borrowing, reserves, partner contributions etc.),
  `multi_year_capital_project_budgets_total_open_project_budget_in_2026`,
  `multi_year_capital_project_budgets_previously_approved_from_prior_capital_plans`.

If you later want a funding-source dimension, those splits are the place to start
(they reconcile to the requests total within each project).

## How to load into Power BI

Option A - load these processed CSVs directly (simplest):

1. Power BI Desktop -> Home -> Get Data -> Text/CSV.
2. Import each of the six CSVs in this folder.
3. Model view -> create relationships (all many-to-one, single cross-filter):
   - `fact_capital_finance[account_key]` -> `dim_account[account_key]`
   - `fact_capital_finance[period_key]` -> `dim_period[period_key]`
   - `fact_capital_finance[costcenter_key]` -> `dim_costcenter[costcenter_key]`
   - `fact_capital_finance[business_unit_key]` -> `dim_business_unit[business_unit_key]`
   - `fact_capital_finance[scenario]` -> `dim_scenario[scenario_code]`
   - `dim_costcenter[business_unit_key]` -> `dim_business_unit[business_unit_key]`
     (optional snowflake link; keep single-direction)
4. Paste the measures from `docs/measures.md`.
   Note: measures.md references `dim_period[year_id]`; this schema uses
   `dim_period[period_key]` (same year-grain values). Either rename the column to
   `year_id` on import, or update the measure references to `period_key`.

Option B - keep the Power Query M path. `docs/power-query-m.md` builds an
equivalent model straight from the raw CSVs inside Power BI. These processed CSVs
are the offline / portable equivalent and the artifact the pytest reconciliation
guards.
